# Root Problem

## Use When

- The user states a solution before a problem.
- The problem statement names a tool or a method.

## Technique

Ask why the user wants the item. Repeat the question on each answer.
Stop when the answer names a need, not a method.
Separate the problem from the solution.
Write the problem as a current state, not as a missing feature.
Keep premature design out of the Problem section.

Check:

- The problem exists without the proposed solution.
- The user can state the cost of the problem.

## Failure Mode

The doc solves a solution. The design misses the real need.

Sources:

- Ohno, "Toyota Production System", 1988 (Five Whys).
- Zowghi and Coulin, "Requirements Elicitation: A Survey of Techniques", 2005 (premature design).
